Pipeline overview

Neighbor-drone detection for a drone swarm, onboard, from a single Livox Mid-360 LiDAR. Two stages:

  • Ego-motion compensation (this repo's root, a modified Point-LIO): every LiDAR point is deskewed per-point, causally, using the EKF state estimate at that exact instant -- not per-scan or per-frame, so there's no residual motion blur to correct for downstream (measured: skipping this and using one pose per ~50ms frame instead would introduce 50-100mm of avoidable distortion during aggressive motion, worse for points early in the frame). Near-field points (where a neighbor drone would actually be) bypass the main EKF update and any decimation entirely: zero dropped points, zero added latency, and a nearby target can never pollute the platform's own state estimate.
  • Detection (detection/): background subtraction and dynamic-point detection via a causal reformulation of DUFOMap -- the official method is offline two-pass (sees the whole flight before judging any single frame); this only ever uses history up to the current frame, so it's real-time compatible by construction, not just fast enough in practice.

Runtime optimization (Jetson Orin NX target)

The whole point of the causal reformulation above is to run onboard, in real time, on a Jetson -- not just as an offline analysis tool. Three rounds of work targeted that:

  • Point-LIO hot-path optimization -- profiling-first pass (per-frame timing instrumentation, gated fully off by default) found the per-point EKF update loop, not map maintenance, dominates; converted it to a scalar fast path for the (empirically confirmed, ~always true) single-point measurement case, avoiding Dynamic-sized Eigen heap allocation and a general matrix inverse for what's provably a 1×1 "inverse". Combined with proper Release build flags (-DNDEBUG, -mcpu=cortex-a78ae) and a few more hot-loop fixes, measured per-operation cost on a Jetson Orin NX (MAXN + locked clocks) came out on par with an x86 dev laptop -- e.g. the EKF update itself: 0.0074 ms/call on Jetson vs 0.0081 ms/call on x86. Aggregated per-frame cost (~30 ms) fits comfortably inside the 100 ms budget at the sensor's native 10 Hz frame rate.
  • Far-field point decimation at capture time -- Jetson shouldn't pay compute for points that get thrown away downstream anyway, so far-field points are range-weighted sampled down to a fixed budget (default 5000/frame, near+far combined) before the EKF ever sees them, not just before publishing. Sampling from frame 0 cost the causal detector's cold-start recall badly (0.99 → 0.35 in testing), traced to fewer far-field rays/frame meaning slower to build "confirmed free space" evidence -- fixed with a short full-density warmup window before sampling kicks in. See the measured points/frame transition (real data, not simulated).
  • ROS2 distro portability fixes -- ported the whole stack from Jazzy (dev machine) to Foxy (Jetson's Ubuntu 20.04): several QoS depths inherited from upstream (as high as 200000) exceeded Fast-RTPS's default resource limits under Foxy and crashed the node on startup; fixed across every publisher/subscriber.

Diagnostics that motivated the design

  • Ceiling false-positive root cause pre-fix -- height-vs-reference-map-density diagnostic that identified the ceiling structure causing the false-positive burst, motivating the cylindrical near-field gate fix (PIPELINE.md §2.3).
  • Self-hit trajectory, time-sync verified -- the platform's own LiDAR self-returns, isolated by true odometry-time matching (not just spatial proximity, which was found to be 74% false positives on its own).
  • CAD target-drone point-cloud template -- reference point cloud used to reason about how many LiDAR points a target drone contributes at typical near-field ranges.
